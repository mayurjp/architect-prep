# Architect Prep — Learning Site: Design Spec

Handoff document for Claude Code. Goal: a GitHub Pages static site that serves a growing bank of
interview/learning Q&A across a full .NET-centric backend curriculum, at Beginner / Intermediate /
Advanced (+ Scenario) levels, with a daily "today's questions" rotation, full browse/search, and a
documented way to add new topics — all with **zero AI calls and zero internet fetches at runtime**.
Content is authored once (by you, using an LLM, offline from the site) and the site only serves and
rotates static data forever after.

## 1. Constraints that shaped this design

- **No AI at runtime.** New questions are never generated by the live site. All content is pre-written
  markdown checked into the repo.
- **"New content daily" without new content.** Resolved via a deterministic client-side rotation engine
  (see §7) that reshuffles which existing questions are "featured" each day, cycling through the full
  bank before repeating.
- **Static hosting only.** GitHub Pages serves files; there is no server, no database, no API route.
  All "build" work (parsing markdown → JSON, generating pages) happens ahead of time via a Node script,
  run locally or in a GitHub Action on push — never at request time.
- **Content already exists in an inconsistent shape.** Four raw files were produced across different
  chat sessions using slightly different conventions (see §3, §9). The design normalizes future content
  to one convention; existing files need a one-time light cleanup.

## 3. Canonical markdown convention

Every future generation session should produce content in this exact shape, so the build script can
parse any topic file the same way:

```markdown
# {Topic Display Name} — Q&A

## {Level} — Question {N}

**Q{N}: {question text}**

{answer body — plain markdown: prose, ### sub-headings, tables, fenced code blocks, ASCII diagrams}

#### Follow-up: {follow-up question text}

{follow-up answer body}

---
```

Rules:
- `{Level}` is one of exactly: `Beginner`, `Intermediate`, `Advanced`, `Scenario`. (`Scenario` is the
  troubleshooting/system-design tier introduced by the microservices file — keep it as a 4th tier
  available to any topic, not just microservices.)
- Numbering restarts at 1 within each `(topic, level)` pair, matching what the source files already do.
- `#### Follow-up: ...` is optional and repeatable; each one becomes a nested Q&A under its parent
  question. This captures the PUT-vs-PATCH / Safe-vs-Idempotent style deep dives seen in the HTTP file.
  Anything indented under `### ` other headings is just part of the main answer body, not a follow-up.
- A horizontal rule (`---`) separates every question (including follow-ups) from the next.
- Code fences must declare a language (`csharp`, `sql`, `yaml`, `json`, `http`, `bash`, `dockerfile`) so
  syntax highlighting works without guessing.
- A question that's only a title with no answer yet (like the Part B banks) is written as:
  ```markdown
  ## {Level} — Question {N}

  **Q{N}: {question text}**

  *(Planned — not yet answered.)*

  ---
  ```
  The build script treats `*(Planned — not yet answered.)*` as the signal for `status: planned` and
  excludes that question from the daily rotation until it's filled in.

## 4. Content schema (derived at build time, not hand-authored)

The markdown files are the source of truth. The Node build script (§6) parses them into one JSON index —
you never hand-write JSON. Each question becomes:

```json
{
  "id": "aspnet-webapi-rest-http__beginner__1",
  "topic": "aspnet-webapi-rest-http",
  "level": "beginner",
  "seq": 1,
  "question": "What is HTTP, and what are its core components (methods, status codes, headers)?",
  "status": "answered",
  "answerHtml": "<p>...</p>",
  "followUps": [
    { "question": "Why is PATCH not idempotent while PUT is?", "answerHtml": "<p>...</p>" },
    { "question": "Explaining the \"Safe\" column in more depth", "answerHtml": "<p>...</p>" }
  ]
}
```

`id` is deterministic (`topic__level__seq`) so it's stable across rebuilds — important for the rotation
engine's "don't repeat until the pool cycles" bookkeeping (§7) and for deep links.

Everything under `/docs` is generated by `scripts/build.js` from `/content` — never hand-edit files in
`/docs`. This mirrors the earlier decision: content lives as markdown, the "AI touches content once, at
seed time" boundary sits at the `/content` folder edge, and everything downstream is deterministic code.

## 6. Build pipeline

`scripts/build.js` (plain Node, no framework required):

1. Read every `/content/*.md` file.
2. Parse using the canonical convention (§3) — split on `## {Level} — Question {N}`, extract the bold
   question line, the answer body up to the next `#### Follow-up:` or `---`, and any follow-ups.
3. Validate: level is one of the 4 allowed values, question numbering has no gaps, every code fence has
   a language tag. Fail the build with a clear error pointing at the offending file/line rather than
   silently emitting bad data — this matters because content authoring happens in a separate AI session
   where mistakes are easy to introduce.
4. Render each answer body from markdown to HTML (a small library like `markdown-it` is enough; no need
   for a full static site generator).
5. Emit `/docs/data/questions.json` (the full index) and `/docs/data/topics.json`.
6. Optionally emit per-topic pre-rendered HTML fragments if you want faster first paint than pure
   client-side rendering — not required for v1.

Run via `.github/workflows/build-deploy.yml` on every push to `main` that touches `/content/**` or
`/scripts/**`: checkout → `node scripts/build.js` → deploy `/docs` to GitHub Pages. No LLM calls, no
external HTTP requests — the workflow only runs the parser.

## 7. The daily rotation engine (no AI, no network)

Goal: the homepage shows a different, evenly-distributed slice of the existing question bank every day,
without repeating a question until every question in that pool has been shown once.

Pure client-side JS, seeded by the calendar date (UTC) so every visitor sees the same "today" set:

```js
// mulberry32 — small deterministic PRNG, seeded from a string (no Math.random, no Date.now at build time)
function seededShuffle(items, seedStr) {
  let seed = 0;
  for (const ch of seedStr) seed = (seed * 31 + ch.charCodeAt(0)) >>> 0;
  const rand = () => {
    seed |= 0; seed = (seed + 0x6D2B79F5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
  const arr = items.slice();
  for (let i = arr.length - 1; i > 0; i--) {
    const j = Math.floor(rand() * (i + 1));
    [arr[i], arr[j]] = [arr[j], arr[i]];
  }
  return arr;
}

// A "cycle" is a full pass through a topic+level's questions in a shuffled, fixed order.
// dayIndex = days since a fixed epoch; cycleLength = pool size; position = dayIndex % cycleLength.
function todaysQuestion(pool, topic, level, todayUtcString) {
  const cycleSeed = `${topic}:${level}`;           // shuffle order is fixed per pool, reshuffled only when the pool size changes
  const order = seededShuffle(pool.map(q => q.id), cycleSeed);
  const epoch = Date.UTC(2026, 0, 1);
  const dayIndex = Math.floor((Date.parse(todayUtcString + "T00:00:00Z") - epoch) / 86400000);
  const position = ((dayIndex % order.length) + order.length) % order.length;
  return order[position];
}
```

Only `status: "answered"` questions are eligible for rotation; `planned` ones are visible in Browse
(marked "coming soon") but never selected as "today's question." The homepage picks one rotating
question per topic (11 topics → 11 cards) plus lets the user jump straight to Browse for everything else.
Because the shuffle is seeded and pure, this needs zero storage, zero server, and produces the same
result for every visitor on the same UTC day — genuinely "new content daily" from a finite, static bank.

## 8. Site pages

- **Today** (`index.html`) — one rotating question per topic, level shown as a badge, click to expand
  the full answer inline (accordion) or navigate to the topic page.
- **Topics** (`topics.html`) — grid of all 11 (growing) topics with question counts per level and a
  progress indicator (answered vs planned).
- **Topic** (`topic.html?t=<slug>`) — tabs for Beginner / Intermediate / Advanced / Scenario (tab hidden
  if a topic has no Scenario content), full question list per tab, follow-ups nested under their parent.
- **Search** (`search.html`) — simple client-side substring/keyword filter over `questions.json`; no
  backend needed since the whole index is a static JSON file small enough to ship to the browser.

## 10. Content generation workflow (offline, human-in-the-loop, not part of the site)

This stays completely outside the site's runtime — it's how *you* keep the `/content` folder growing.

1. Use the canonical prompt template (`PROMPT-TEMPLATE.md`, provided alongside this spec) in any AI
   chat session, filling in the topic/area and level, generating in batches of 5 as before.
2. Paste the output into the matching `/content/<slug>.md` file, following the §3 heading convention.
3. Run `node scripts/build.js` locally to validate formatting and preview the new content.
4. Commit and push — the GitHub Action rebuilds and redeploys automatically.
5. To add a brand-new topic beyond the current 11: create `/content/<new-slug>.md` with the §3 header,
   add an entry to `/content/topics.json` (id, title, description, color/icon, order), then repeat
   steps 1–4. No code changes required — this is the entire "add a topic" workflow promised at the
   start of this project.

## 11. Explicitly out of scope for v1 (optional future work)

- A non-AI "What's New" feed pulling official release notes (.NET, Kubernetes, GCP, EF Core) via a
  scheduled job — discussed earlier as a way to reintroduce genuine internet freshness without AI or
  fabricated Q&A. Not built now; the rotation engine (§7) already satisfies "feels new every day."
- Spaced-repetition / self-tracked progress (would need `localStorage`, which is fine for a real
  GitHub Pages deployment even though it's disallowed inside Claude-generated *artifacts* specifically).
- Full-text fuzzy search / tagging by sub-topic — v1 search is a plain substring filter.
