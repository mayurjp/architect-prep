# Docker — Q&A

## Beginner — Question 1

**Q1: What is the difference between a Docker Image and a Docker Container?**

- **Docker Image:** An immutable, read-only template that contains the application code, libraries, dependencies, tools, and other files needed to make an application run. It is built from a set of instructions defined in a `Dockerfile`. Think of it as a class in OOP, or a compiled `.exe` file.
- **Docker Container:** A running instance of a Docker image. When you start an image, Docker adds a read-write layer on top of the image (the container layer) and isolates its execution using Linux namespaces and cgroups. Think of it as an object instantiated from a class, or the running process of that `.exe`.

#### Follow-up: Why are Docker containers so much faster to start than Virtual Machines (VMs)?
VMs require a full guest Operating System (OS) to boot up, which includes a kernel and background services. A Docker container shares the host machine's OS kernel. Starting a container is effectively just starting a standard process on the host machine, which takes milliseconds instead of minutes.

## Intermediate — Question 1

**Q1: Explain the structure of a `Dockerfile` and the concept of Layer Caching.**

A `Dockerfile` is a text document that contains all the commands a user could call on the command line to assemble an image.

**The Mechanism:**
Each command in a `Dockerfile` (e.g., `FROM`, `RUN`, `COPY`, `CMD`) creates a new "layer" in the image. These layers are stacked on top of each other. 
When you run `docker build`, Docker checks if it already has a layer built for that exact command. If it does, it uses the cached layer instead of rebuilding it.

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
# 1. Copy ONLY the project file first
COPY ["MyApp.csproj", "./"]
# 2. Run restore (This layer caches heavily)
RUN dotnet restore "MyApp.csproj"
# 3. Copy the rest of the source code
COPY . .
# 4. Build and publish
RUN dotnet publish -c Release -o /app/publish
```

**Common Pitfalls (Cache Invalidation):**
If a layer changes, *all subsequent layers* are invalidated and must be rebuilt. 
If you simply `COPY . .` first and then `RUN dotnet restore`, changing a single HTML file in your project will invalidate the `COPY` layer. This forces Docker to re-download all NuGet packages on every build, severely slowing down CI/CD pipelines. The best practice is to copy only the dependency files (`.csproj`, `package.json`) first, restore, and *then* copy the rest of the source code.

## Intermediate — Question 2

**Q2: What is a Docker Volume and why is it necessary?**

By default, any data created or modified inside a running container is written to the container's read-write layer. When the container is deleted, that data is lost forever.

**The Mechanism:**
A **Volume** is a mechanism for persisting data generated by and used by Docker containers. Volumes are stored on a part of the host filesystem which is managed by Docker (typically `/var/lib/docker/volumes/` on Linux) and are completely isolated from the container's lifecycle.

When you mount a volume to a container (e.g., mapping `/var/lib/mysql` in the container to a volume), the container writes directly to the host disk. If the container crashes or is deleted, the data remains safely in the volume and can be attached to a new container.

#### Follow-up: What is a Bind Mount and how is it different from a Volume?
A Bind Mount allows you to map any specific file or directory on the host machine directly into a container. Unlike volumes (which Docker manages entirely), bind mounts depend on the directory structure of the host machine. They are primarily used during local development (e.g., mounting your local source code folder into the container so changes reflect instantly without rebuilding the image).

## Advanced — Question 1

**Q1: Explain how Docker Networking works. What are the default network drivers?**

When containers are running, they often need to communicate with each other or with the outside world. Docker handles this via its networking subsystem.

**The Network Drivers:**

1. **Bridge (Default):** 
   - When you start a container without specifying a network, it connects to the default `bridge` network. 
   - Containers on the same bridge network can communicate via IP address.
   - **Important:** The default bridge does *not* support automatic DNS resolution between containers. To get DNS (where Container A can ping `http://container-b`), you must create a *user-defined bridge network*.
   
2. **Host:** 
   - Removes network isolation between the container and the Docker host. 
   - If a container binds to port 80, it takes port 80 on the host machine directly. It is highly performant but restricts you to running only one instance of that container (due to port collisions).

3. **None:** 
   - Completely disables all networking for the container. It is completely isolated.

4. **Overlay:** 
   - Used in distributed environments like Docker Swarm (or Kubernetes setups using Docker engines). It allows containers running on entirely different physical host machines to communicate securely over a virtual network.

**Common Pitfalls:**
Relying on IP addresses to communicate between containers. Container IP addresses change every time they are recreated. Always create a user-defined network and communicate using the container's name as the hostname.

## Advanced — Question 2

**Q2: Explain the differences between Docker Compose and a full orchestrator like Kubernetes.**

Both tools are used to run multi-container applications, but they operate at completely different scales.

**Docker Compose:**
- **Scope:** Runs on a *single host machine*. 
- **Mechanism:** You define all the services (containers), networks, and volumes in a single `docker-compose.yml` file. You run `docker-compose up`, and the Docker engine on that single machine spins everything up.
- **Use case:** Local development environments (spinning up a local API, SQL Server, and Redis cache at once) or very small, single-server production deployments. It does not handle automated failover across machines.

**Kubernetes (K8s):**
- **Scope:** Runs across a *cluster of multiple host machines* (Nodes).
- **Mechanism:** You declare the desired state, and a highly distributed control plane constantly monitors the cluster. If a Node's hard drive fails and 10 containers die, Kubernetes automatically reschedules those containers onto healthy Nodes in the cluster.
- **Features:** It includes built-in load balancing across machines, rolling deployments with zero downtime, autoscaling based on CPU usage, and secret management.
- **Use case:** Enterprise-scale, highly available production environments where downtime is unacceptable and workloads require dozens or hundreds of servers.

## Scenario — Question 1

**Q1: You are containerizing an existing ASP.NET Core web application. The application reads a sensitive database connection string and a third-party API key on startup. How do you pass these secrets securely into the Docker container without exposing them?**

Never hardcode secrets in your code, and **never hardcode secrets directly into your `Dockerfile`** using `ENV` instructions. If you put a secret in a `Dockerfile`, anyone with access to the image can run `docker history` and see the secret in plain text.

**The Solution:**
You must provide secrets at **runtime**, not at build time. 

**The Mechanism:**
1. **Local Development:** When running the container locally, use an environment variables file (`.env`).
   - Create a `.env` file containing `DB_CONNECTION_STRING=SecretValue123`.
   - Add `.env` to your `.gitignore` immediately so it is never committed to source control.
   - Run the container using: `docker run --env-file ./.env my-aspnet-app`. Docker securely injects the variables into the running container process.
2. **Production:** When deploying to production (e.g., Azure Container Apps, Kubernetes, or AWS ECS), you do not use `.env` files.
   - You store the secrets in the cloud provider's secure vault (Azure Key Vault, AWS Secrets Manager, or Kubernetes Secrets).
   - You configure the orchestrator to securely inject those vault values as environment variables into the container right as it boots up.
3. **.NET App Code:** Your application code remains identical across all environments. It simply calls `builder.Configuration.GetConnectionString("DB_CONNECTION_STRING")`. The standard .NET configuration provider automatically reads the environment variable, regardless of how it was injected.

## Scenario — Question 2

**Q2: You build a Docker image for a .NET API. The resulting image is 800MB. When you deploy to production, it takes minutes to download the image, slowing down scaling. How do you significantly reduce the size of this Docker image?**

Large images happen when developers bundle the entire SDK, build tools, and source code into the final production image.

**The Solution: Multi-Stage Builds**
You must separate the "build" environment from the "runtime" environment using a Multi-Stage `Dockerfile`.

**The Mechanism:**
1. **The Build Stage (Heavy):** You start with a heavy base image that contains the full .NET SDK (`mcr.microsoft.com/dotnet/sdk:8.0`). You copy your source code in, run `dotnet restore`, and `dotnet publish`. This stage might be 800MB+.
2. **The Runtime Stage (Lightweight):** In the *same* `Dockerfile`, you start a second `FROM` instruction, this time using the much smaller ASP.NET Runtime image (`mcr.microsoft.com/dotnet/aspnet:8.0`), which only contains what is needed to run a compiled app, not build it.
3. **The Transfer:** You use `COPY --from=build` to copy *only* the compiled DLLs from the first stage into the second stage.

**Result:**
When Docker finishes building the image, it completely discards the heavy "build" stage. The final production image only contains the lightweight runtime base and your compiled DLLs, often reducing the image size from 800MB down to < 100MB. This drastically speeds up deployment times.

## Scenario — Question 3

**Q3: You deploy a Docker container containing a .NET web API to a production Kubernetes cluster. The cluster security policy suddenly rejects your pod with a `PrivilegeEscalation` or `RunAsRoot` violation. Why did this happen, and how do you fix it in your Dockerfile?**

By default, Docker containers run their processes as the `root` user. While this `root` user is isolated within the container, running as root is a major security risk. If a vulnerability allows an attacker to break out of the container, they will have root access to the host machine. Modern secure environments (like strict Kubernetes clusters) explicitly forbid containers from running as root.

**The Solution:**
You must configure your Dockerfile to run the application as a non-root user.

**The Mechanism:**
In standard .NET Docker images, Microsoft provides a built-in non-root user specifically for this purpose.
You simply add a `USER` instruction to your Dockerfile right before the `ENTRYPOINT`.

```dockerfile
# ... build stages ...

FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /app/publish .

# Switch to the non-root 'app' user using its UID
USER $APP_UID

ENTRYPOINT ["dotnet", "MyApp.dll"]
```

**Result:**
The container process now runs with restricted permissions. If the application is compromised, the attacker only has standard user privileges within the container namespace, drastically reducing the blast radius.

## Beginner — Question 2

**Q2: What is the difference between `CMD` and `ENTRYPOINT` in a Dockerfile?**

Both define what runs when a container starts, but they interact very differently with arguments passed on the `docker run` command line.

**`CMD` — a default, fully overridable:**
```dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:8.0
ENTRYPOINT ["dotnet", "MyApp.dll"]
CMD ["--environment=Production"]
```
```bash
docker run my-image                        # runs: dotnet MyApp.dll --environment=Production
docker run my-image --environment=Staging  # CMD is completely replaced: dotnet MyApp.dll --environment=Staging
```

**`ENTRYPOINT` — the fixed executable, arguments are appended to it (not replacing it):**
```bash
docker run my-image --urls=http://+:8080   # runs: dotnet MyApp.dll --urls=http://+:8080
```
Whatever you pass on the command line gets appended *after* the `ENTRYPOINT`'s command, rather than replacing it entirely (unless you override `ENTRYPOINT` itself with `--entrypoint`).

**The common pattern:** use `ENTRYPOINT` for the fixed, non-negotiable part of the command (the executable itself — `dotnet MyApp.dll`), and `CMD` for default arguments a caller might reasonably want to override (like a default environment or config flag). This is why most real Dockerfiles combine both rather than using either alone.

**Common Pitfall:** using the *shell form* (`CMD dotnet MyApp.dll` without brackets) instead of the *exec form* (`CMD ["dotnet", "MyApp.dll"]`). The shell form runs your command as a child process of `/bin/sh -c`, meaning `SIGTERM` signals sent by Docker/Kubernetes go to the shell, not your actual application — your app never gets a chance to shut down gracefully, and Docker eventually escalates to `SIGKILL` after the grace period, unnecessarily. Always use the exec (array) form for `CMD`/`ENTRYPOINT`.

## Intermediate — Question 3

**Q3: What is Docker Compose, and how does a minimal `docker-compose.yml` for a .NET API + SQL Server look?**

Docker Compose lets you define and run a multi-container application (an API, its database, a cache) as a single unit, described declaratively in one YAML file, instead of manually running several `docker run` commands with matching network/volume flags.

```yaml
version: "3.9"
services:
  api:
    build: .                          # builds from the Dockerfile in this directory
    ports:
      - "8080:8080"
    environment:
      - ConnectionStrings__Default=Server=db;Database=AppDb;User=sa;Password=${DB_PASSWORD}
    depends_on:
      - db

  db:
    image: mcr.microsoft.com/mssql/server:2022-latest
    environment:
      - ACCEPT_EULA=Y
      - MSSQL_SA_PASSWORD=${DB_PASSWORD}
    ports:
      - "1433:1433"
    volumes:
      - sql-data:/var/opt/mssql        # named volume — survives container recreation

volumes:
  sql-data:
```

Running `docker compose up` builds the `api` image, pulls the `db` image, creates a shared user-defined network (so `api` can reach `db` by that hostname automatically), and starts both containers together.

**Key details:**
- **`depends_on`** controls *start order* only — it does **not** wait for SQL Server to actually finish initializing and accept connections, just for its container process to start. A common follow-up fix is a retry/backoff policy in the API's own DB connection logic (e.g., EF Core's `EnableRetryOnFailure()`) to ride out that gap.
- **Named volumes** (`sql-data`) persist database files across `docker compose down`/`up` cycles — without one, a `docker compose down` (which removes containers) would silently wipe the database.
- **Environment variable substitution** (`${DB_PASSWORD}`) lets you keep secrets out of the committed YAML file, typically supplied via a `.env` file (gitignored) sitting next to `docker-compose.yml`.

**Common Pitfall:** relying purely on `depends_on` as a substitute for a proper health-check-based startup order — for anything beyond local dev convenience, pair it with `condition: service_healthy` and a `healthcheck:` block on the `db` service so `api` genuinely waits for SQL Server to be ready, not just "started."

## Advanced — Question 3

**Q3: What is the difference between a Docker image's `COPY` and `ADD` instructions, and why is `COPY` usually preferred?**

Both instructions copy files from the build context into the image, but `ADD` has extra "magic" behaviors that are easy to trigger by accident.

```dockerfile
COPY appsettings.json /app/appsettings.json    # copies exactly this file, nothing more
ADD source.tar.gz /app/                        # ADD automatically extracts recognized archives!
ADD https://example.com/file.txt /app/         # ADD can also fetch remote URLs
```

**What `ADD` does beyond `COPY`:**
- If the source is a **recognized compressed archive** (`.tar`, `.tar.gz`, `.tgz`, etc.), `ADD` automatically extracts it into the destination — `COPY` never does this; it copies the archive file as-is.
- `ADD` can fetch a **remote URL** directly into the image — `COPY` only works with local build-context files.

**Why `COPY` is the recommended default:**
- **Predictability:** `COPY` does exactly one thing — copy files/directories verbatim. There's no implicit archive-extraction behavior to be surprised by if a filename happens to end in `.tar.gz` for unrelated reasons.
- **Layer caching implications:** `ADD`'s URL-fetching behavior means the fetched content isn't tracked for cache-invalidation the way a local file's checksum is — a remote file changing wouldn't necessarily invalidate the build cache, silently baking a stale file into your image.
- **Security:** `ADD`'s URL-fetch feature pulls arbitrary remote content into your build with no built-in integrity verification (no checksum pinning) — a compromised or MITM'd URL could inject malicious files into your image during the build.

**When `ADD` is still the right tool:** the auto-extraction behavior is occasionally genuinely useful (unpacking a downloaded SDK tarball as part of a build stage) — but even Docker's own official documentation recommends `COPY` plus an explicit `RUN tar -xzf ...` for anything beyond that narrow case, specifically so the extraction step is visible and intentional in the Dockerfile rather than an implicit side effect of the instruction you chose.

## Beginner — Question 3

**Q3: What is a Docker Registry, and how does an image name/tag (e.g., `mcr.microsoft.com/dotnet/aspnet:8.0`) map to it?**

A Registry is a storage and distribution service for Docker images — Docker Hub is the default public registry, but organizations commonly run private registries (Azure Container Registry, AWS ECR, GitHub Container Registry) for their own images.

**Anatomy of an image reference:**
```text
mcr.microsoft.com/dotnet/aspnet:8.0
└────────┬───────┘└─────┬────┘└┬┘
     registry         repository  tag
     (host)           (image name) (version)
```
- **Registry host** — where the image is stored/pulled from; omitting it defaults to Docker Hub.
- **Repository** — the image's name, often with a namespace (`dotnet/aspnet` groups related Microsoft-published images).
- **Tag** — a human-readable version label (`8.0`, `latest`, `8.0.1-alpine`) pointing to a specific image build.

**Pulling and pushing:**
```bash
docker pull mcr.microsoft.com/dotnet/aspnet:8.0        # download from the registry
docker tag my-api:latest myregistry.azurecr.io/my-api:1.4.2  # re-tag for a private registry
docker push myregistry.azurecr.io/my-api:1.4.2          # upload to the private registry
```

**Common Pitfall:** relying on the `latest` tag in production deployments — `latest` is just a convention (a mutable pointer that a `docker push` can silently move to point at a completely different image), not a guarantee of "the newest stable version." A deployment pinned to `latest` can pull a different image today than it did yesterday with zero code change on your end, defeating reproducible deployments; pin to an explicit version tag (or better, an immutable image digest) instead.

## Intermediate — Question 4

**Q4: What is a Docker health check, and how does it differ from a Kubernetes liveness/readiness probe?**

Both answer "is this container actually healthy," but a Docker-native `HEALTHCHECK` operates at the single-container level (visible via `docker ps`), whereas Kubernetes probes are what actually drive orchestration decisions (routing traffic, restarting pods) when running under Kubernetes — the two overlap in purpose but aren't the same mechanism.

**Docker-native health check (in the Dockerfile):**
```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1
```
Docker runs this command periodically inside the running container and marks it `healthy`/`unhealthy`/`starting` — visible via `docker ps` (showing `Up 2 minutes (healthy)`), useful for local development and `docker-compose`'s `depends_on: condition: service_healthy`.

**Kubernetes probes (in the Pod spec) — this is what actually matters in a K8s cluster:**
```yaml
livenessProbe:
  httpGet: { path: /health/live, port: 8080 }
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
```
Kubernetes **does not read or use the Dockerfile's `HEALTHCHECK` directive at all** — it has its own, separate probe configuration in the Pod spec, and this is what actually determines whether traffic is routed to a Pod (readiness) or whether it gets restarted (liveness).

**Why this distinction trips people up:** a team migrating a `docker-compose`-based setup (relying on `HEALTHCHECK`) to Kubernetes often assumes the existing Dockerfile health check "just works" in the new environment — it doesn't; Kubernetes-specific `livenessProbe`/`readinessProbe` configuration must be added separately in the Pod/Deployment manifest, since Kubernetes has no awareness of the Dockerfile's `HEALTHCHECK` instruction whatsoever.

**Common Pitfall:** defining a Dockerfile `HEALTHCHECK` and assuming that alone provides production-grade health monitoring once deployed to Kubernetes — it's inert there; Kubernetes-native probes are the only mechanism that actually affects traffic routing and restart behavior in a K8s cluster.

## Advanced — Question 4

**Q4: What are Docker build cache mounts (`--mount=type=cache`), and how do they solve a caching problem that layer caching alone can't?**

Regular Docker layer caching (covered earlier) caches an entire `RUN` instruction's result as one layer — but package manager caches (NuGet, npm) inside that layer are still thrown away and rebuilt from scratch whenever the layer needs to rebuild at all, even for a tiny dependency change. Cache mounts solve this by persisting a specific *directory* across builds, independent of the layer cache.

**Without a cache mount — restoring dependencies re-downloads everything on any cache miss:**
```dockerfile
COPY ["MyApp.csproj", "./"]
RUN dotnet restore "MyApp.csproj"  # if this layer needs to rebuild, EVERY package re-downloads from scratch
```

**With a cache mount — the NuGet package cache persists across builds, even when the layer itself rebuilds:**
```dockerfile
COPY ["MyApp.csproj", "./"]
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet restore "MyApp.csproj"
```
The `/root/.nuget/packages` directory is preserved in a special build cache **outside** the resulting image layer, persisting across separate `docker build` invocations even when the `.csproj` changes and the `RUN` instruction's own layer cache is invalidated — so only *newly added or changed* packages need to be downloaded, not the entire dependency graph from scratch.

**Why this is a distinct mechanism from layer caching:** layer caching works at the granularity of "did this entire instruction's inputs change" (all-or-nothing per layer); a cache mount instead persists a specific *directory's contents* across builds regardless of whether the layer itself was cache-hit or cache-miss, solving the specific pain of "even a one-line dependency addition forces a multi-minute full package re-download."

**Common Pitfall:** using cache mounts but forgetting they require BuildKit (`DOCKER_BUILDKIT=1`, the default in modern Docker) and aren't portable to every CI environment without configuration — some CI runners' Docker layer caching setups (e.g., certain remote-cache configurations) need explicit configuration to actually persist cache-mount contents between CI runs, since a fresh CI runner with no persisted build cache gains nothing from a cache mount on its very first build.
